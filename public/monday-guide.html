A map of the submission: the case, what is not proven yet, the live system, the code, and the evidence. Every path is as it sits in the submission ZIP. Using a coding agent? The prompt is at the end.

1 · The case

In one line: a modest build that listened. The model picks clauses; code decides what governs and checks every number, so the system says "not addressed" or "needs review" instead of guessing. Doug, Nina, Elena and Sam Ito are the four RET stakeholders from the brief.
Brief sectionWhat it covers
1.1 Executive summary15 business days to a brief today; facts the same day, answers in minutes, cited
1.2 Pain points and business case~650 hours a cycle, ~$1.6M a year; four people, three pains each, in their words
1.3 Technical architectureLives in monday.com; three boards; what leaves RET (~3,400 characters a question)
ProofThe worst run first; under $1 of AI a cycle
1.4 Scalable rolloutPilot, all cycles, next teams, each with an exit test; what this pilot will not build
1.5 Product recommendationsUsage visibility below Enterprise, cheaper unchanged writes, AI columns that cite

2 · Not proven yet

  • Real PDFs and 400–600 page RFPs. A real Army Corps of Engineers package was tried once and parsed to zero clauses; unknown formats are now refused with a reason. Only the 118-page text file works today.
  • The model under a real attack. What can leave is bounded and tested; injection resistance on the real model is not proven (the war game ran on a mock).
  • Crash recovery mid-write, 429s, 200-with-errors. Handled in code; no test forces them.
  • Claude's temperature is not pinned (rfp/provider.py, line 147); one case flips about one run in ten.
  • Vague amendment wording. "Adjusted" is not on the change list (rfp/resolve.py, line 39); the better default flags every unclassified clause.
  • Accuracy on RET staff's own questions: what the pilot measures first.

Before real client data: client-owned credentials in a secrets manager, access control for the bid team, retention set by RET's policy. After the proof of concept, for peer review: promptfoo or RAGAS evals and a Sensei suite, OpenTelemetry tracing, CI running the same gates.

3 · The live system

  1. Solicitation package: Key Facts board (source/docs/site/monday-key-facts.jpg; both boards explained in source/docs/site/boards.html). The proposal deadline (Dec 4, Amendment §A1.1 governs, §3.2 replaced) and the bid deposit ($75,000 to $100,000, §A1.2).
  2. Internal questions: Questions board (source/docs/site/monday-questions.jpg). RET's 14 sample questions, answered with citations. A blank Call ID means no LLM call: key facts are quoted deterministically from the governing clause.
  3. A new question: added on the board; the poller picks it up within a minute and answers with citations. Every model call and monday.com call is logged (source/flightlog/).
  4. One answer traced: ./rfp ask --json "When are proposals due?", then ./rfp verify-proof, run from source/. The saved trace is source/docs/site/proof-of-one-answer.html.

For your agent. This page is a map; the ZIP is the territory. The full file list is in the ZIP as source/docs/catalog.json and is printed in plain HTML in section 5. A prompt to paste into Claude Code (or any coding agent) next to the unzipped submission:

1. Unzip the submission. Read source/README.md first.
2. Read the two guardrails:
• source/source/rfp/answer.py, around line 329: the figure check. Every number must appear word for word in a cited clause, or the answer is withheld.
• source/source/rfp/resolve.py, line 45: the amendment rules. Code decides which text governs.
3. From source/source, run: python3 -m unittest (no API key needed; it uses a mock model).
4. Tell me where these guardrails could still fail, and which test would catch it.

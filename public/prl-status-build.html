02

Findings & what's ruled out

Everything confirmed from live evidence (the CRM, the automation history, the site, and DNS lookups). Ruled-out rows are struck through with the reason they're off the table — so we don't re-litigate them.

Root cause (narrowed)
Only the Tidio delivery node is missing — the rest is proven
Capture fires (26 runs, but Leads acquired = 0), and the Zapier → SugarCRM write is now proven in the sandbox. The single remaining gap: the Tidio flow has no webhook / delivery node to hand the lead off. The "lead delivery bridge" flow is an off draft with no webhook step. (Closes A-2 and A-6.)
Confirmed
Chatbot → SugarCRM lead creation works end-to-end (sandbox)
A dedicated zapier.chatbot integration user + a sandbox-pinned connection create a Lead with the full field map. lead_source = Chatbot is accepted — a value that exists only in the sandbox — and it auto-routes to a rep. Test lead created, verified in-app, and deleted.
Confirmed
Field-map correction: Location uses state abbreviations
location_c takes abbreviations (CT, CA, NY), not full state names. The Zapier transform must map to these exact keys.
Confirmed
Sugar's Zapier connection needs a dedicated local user, not an SSO login
An SSO account (e.g. todd.hotes) can't do the password grant Zapier requires. A dedicated local user (zapier.chatbot) authenticates cleanly on the base platform.
Root cause
The website forms don't use the sender that already exists
Form notifications go out under a previous vendor's domain, so they fail authentication and get filtered — while a fully configured prlresins.com sender sits unused.
Confirmed
The email-authentication stack is already in place and correct
DNS lookups confirm a complete Mailgun sending domain on mg.prlresins.com (sender policy, signing key, routing, tracking), Mailgun authorized on the root domain, an enforcing domain policy, Microsoft 365 signing, and Barracuda in front of inbound mail. This was set up properly.
Confirmed
Inbound mail into Tidio works; the "more spam" is a different surface
Email reaches the shared box and becomes Tidio tickets. The recent noise is inbound cold email to a public address, not website-form spam — so the form spam controls don't touch it.
Confirmed
The form spam-controls are on staging, not live yet
The honeypot, speed check, and material-type field exist on the staging copy; the live contact form still shows the old field set.
Ruled out
The domain needs new SPF / DKIM / DMARC records
Why: all present and correct in DNS. No DNS work is required — touching it would add risk, not remove it.
Ruled out
Major domain work is needed before forms can send
Why: the sender already exists. The remaining need is a send-only key handed to the site, not new setup.
Ruled out
The chatbot pipe is blocked on CRM admin access
Why: admin access to the CRM is already in hand (verified by making a live config change in the test environment this week).
Ruled out
Emailing the shared box is a safe way to alert on a new lead
Why: the enforcing domain policy plus Barracuda would quarantine an unauthenticated alert, and the box is noisy. Alerts must ride the authenticated sender and land somewhere dedicated.
Ruled out
The Gravity Forms cleanup will cut the inbox spam Todd sees
Why: that spam is inbound email to the shared box, a separate surface. Form controls only screen website submissions.

# RestOfThePlan — Volunteer Segment Briefs

Four structured briefs for the volunteer segments identified in the audit benchmark plan.
Each: what it is / what's in place / what's missing / next step. ~150-200 words.

---

## 1. Seed Enrichment — Somatic Self-Report Hook

**What it is.** A 6-question felt-sense check added at intake, before the compass runs, that raises the somatic layer from DEFAULT (conservative auto-filled values) to user_self_report. The six questions map to the six phenomenological primitives (phase_tuning, surge_detection, feels_right, that_vibes, locked_in, expected_vs_actual), scored 0–1 each. This is the cleanest way to get real somatic signal into the operator pipeline without adding sensors or live observation.

**What's in place.** The `somaticPrompt` constant is already written in `src/lib/audit-translator.ts` (lines 386–396) — all six questions, the 0–1 scoring instruction, and the skip-for-defaults escape hatch. The translator has the code to consume six scores and set `somatic.source = "user_self_report"`. The fidelity tagging framework (D5) is locked: pairs are tagged by somatic/hci/axioms source from day one, and the benchmark review protocol says proxy/default inputs are lower-confidence evidence. The audit service schema (`schemas.py`) accepts `somatic: Literal["default", "user_self_report"]`. The `SomaticReading` dataclass and witness-score computation exist in `arcs_primitives.py`.

**What's missing.** Nothing collects the six scores from the user. The compass route (`src/app/api/compass/route.ts`) doesn't ask these questions — the intake form sends question/horizon/stakes/clarityMode, not somatic self-report. The somaticPrompt is a string constant sitting in the translator with no path into the request flow. The PRISMA `Receipt` model has no somatic fields (somatic only lives in `OperatorPrimitives`, which are audit-side). There's no UI component, no intake field, no wire from form → translator → somatic.source.

**Next step.** Add the six somatic questions to the prep session or intake form (start with prep — it already captures calibration context), pass the six scores through the compass request body, and wire them into `translateCompassReceipt` so somatic.source becomes "user_self_report" when provided. This is a UX + translator wiring task, not a new operator or schema change.

## 2. ARCS Volunteer-Facing Docs

**What it is.** The operator library is 34 files, 16.6K LOC, spanning four layers (meta-operators, primitives, systems, infrastructure). Two skills already exist to navigate it: `arcs-operator-table` (the structural map — which operators exist, what layer they're on, how they compose, CLI entry points) and `arcs-reading-sequence` (the substrate-first reading protocol — read substrate → structural map → components → synthesis). A volunteer joining the operator effort needs more than navigation — they need to know how to contribute.

**What's in place.** `arcs-operator-table` skill is comprehensive: all 8 meta-operators listed with file/LOC/purpose/invocation, the canonical SAGE→LAB→BAR→CURATOR→KINTSUGI flow, Layer 2 primitives (ARCS Law equation, dataclasses), Layer 3 systems (CIS, HC, LTE, ROM, Trace, Diagnostic), Layer 4 infrastructure (pipeline, runtime, API, CLI runner, store), integration seam points (compass route uses Claude L0–L5 directly; operators are canonical alternative), and the experimental-operator warning (INCHWORM+ECHO, PROFILE-SCAN-FOLKSONOMY are observatory-grade, not decision-gating). `arcs-reading-sequence` skill encodes the anti-pattern corrections (flag inferred dependencies, lower conviction when evidence is thin, invite falsification). The `operators/README.md` has CLI entry points and the four-layer architecture.

**What's missing.** No "developing for ARCS" guide — there's no doc that says: here's the operator contract you implement, here's how to test your operator, here's how to run it through the audit pipeline, here's what "promotion to canonical" means. No onboarding doc that bridges the two existing skills into a contributing flow. Volunteers have no clear path to write an operator that matters — the operator-table says integration is "NOT currently wired into the compass route," which is accurate but discouraging without a path forward. No operator invocation cookbook for volunteers who want to run operators on their own decisions as a learning exercise.

**Next step.** Write a volunteer onboarding doc (1–2 pages) that sequences the existing skills into a contribution flow: (1) load arcs-operator-table + arcs-reading-sequence together, (2) pick a layer and read the substrate first, (3) identify an operator gap or an experimental operator ready for promotion review, (4) implement the operator contract (`arcs_primitives.py` dataclasses + the meta-operator interface), (5) run it through the audit sidecar to generate paired benchmark evidence. This doc doesn't need new content — it orients the existing content toward contribution.

## 3. OPFOR Realism Discipline — LAB Adversarial Lens on Every LLM Output

**What it is.** The discipline that every LLM output should run through an adversarial lens (LAB or equivalent) before being presented to the user or consumed downstream. LAB (`arcs_operators_lab.py`) implements this as a three-lens operator: Loki (structured devil's advocate — challenge statement, failure modes, hidden assumptions, worst case, threat score), Advisors (5-archetype board — SAGE, GUARDIAN, DREAMER, ELDER, SHAPESHIFTER — each with stance, reasoning, confidence), and Bayesian (prior = SAGE NCI/100, Loki shifts belief by threat_score × 0.35, advisor consensus boosts by proceed_fraction × 0.25, posterior clamped [0,1], proceed_recommended at ≥0.65). The output is a `LABAssessment` with integrated threat level (LOW/MEDIUM/HIGH/CRITICAL), recommendation (PROCEED/PAUSE/PIVOT/ABORT), and summary.

**What's in place.** LAB exists as a fully implemented operator (28KB, Phase 3 READ-WRITE, executed and verified). It runs in the audit pipeline as part of the fire-and-forget `runAudit` call (SAGE→LAB→BAR→KINTSUGI, parallelized via Promise.all, gated by `AUDIT_SERVICE_URL`). LAB's `generate_loki_challenge()` auto-generates a Loki challenge from the SAGE receipt's signal classification, five derivatives, and axiom tensions — this is the "default Loki," a programmatic devil's advocate. LAB's `generate_default_advisors()` builds a 5-archetype board from the SAGE receipt state. The audit service re-runs operators on compass primitives; LAB and BAR both re-run SAGE internally. The benchmark plan's subtask table explicitly compares LLM's `reasoning.advisors.loki_challenge` + `loki_counter` against LAB's `loki.challenge_statement` + `loki_threat_score` — the paired-evidence collection for this comparison is built (benchmark_pairs.jsonl, 5 rows flowing).

**What's missing.** The OPFOR discipline is not realized in the compass route's pre-inference path. Only SAGE runs as a pre-screen (via `SAGE_URL` pattern, lines 193–220 of route.ts) — and D4 explicitly says the advisory block is persistence/benchmark-only, NOT injected into LLM context. LAB does not run before the LLM response; it runs after receipt creation, fire-and-forget, in the audit sidecar. The user never sees a LAB assessment. The "every output gets a Loki challenge before presentation" discipline exists only as a benchmark comparison target, not as a runtime guard. There's no synchronous adversarial pre-screen equivalent to the SAGE_URL pattern for LAB. The compass route's LLM output goes straight to the user with only the SAGE advisory block (when SAGE_URL is set) in context — no Loki challenge, no advisor board, no Bayesian posterior gates the response.

**Next step.** The near-term step is the one the plan already architected: accumulate paired evidence (LLM's loki_challenge vs LAB's challenge_statement, LLM's bayesian_risk_pct vs LAB's posterior_confidence) in the benchmark store and review it on the weekly/monthly/quarterly cadence. The OPFOR discipline is aspirational until either (a) LAB becomes a pre-inference pre-screen (a `LAB_URL` pattern parallel to `SAGE_URL`, which D4 currently defers), or (b) the benchmark accumulates enough paired evidence that a specific LAB subtask (e.g., Loki challenge quality) becomes a Path B candidate — meaning LAB's output replaces the LLM's for that subtask in the user-facing response. The discipline is realized by evidence, not by wiring.

## 4. L5 / Runtime Hooks — Post-Compass Composition, Alternate Paths, Anticipatory Briefing

**What it is.** The compass route does L5 synthesis as the final stage of the Claude L0–L5 call — the LLM produces the full receipt (D/E/W/Y state vector, tributaries, court, advisors, fated, paths) in one inference. Runtime hooks are the mechanisms that let the system do something with that receipt after it's created: compose follow-on actions, explore alternate paths, or brief the user anticipatorily (before the T+7 debrief email). The question is what hooks exist, what's missing, and what realizing this would mean.

**What's in place.** The compass route (`src/app/api/compass/route.ts`) creates a `Receipt` (Prisma, full DEWY fields + Y-gate state + macro_tags + tributaries + raw_response) and returns it with `y_state`, `y_conviction`, `render_resolution`, `nci_delta`. Post-compass, there are several non-blocking side effects: (1) fire-and-forget `runAudit` call to the audit sidecar (SAGE/LAB/BAR/KINTSUGI, gated by `AUDIT_SERVICE_URL`), (2) invisible `SageTrace` row written for the SAGE pre-screen efficacy study, (3) receipt confirmation email (T₀ "bearing locked" artifact), (4) scheduled debrief/calibration email (T+7 close-the-loop touchpoint, with debrief opt-in gating). The route supports enriched re-runs via `parentReceiptId` (fetches parent's yState/nciScore/version for session versioning). The `computeYGate` function derives Y-state (GREEN/YELLOW/RED/FORK/SCRATCH/DELTA/PARADOX/DRIFT) from the LLM output + prep context + parent state. The audit sidecar exists as a compositional hook point — operators can re-run on the receipt primitives.

**What's missing.** No explicit post-compass composition layer. The receipt is persisted and emails are fired, but there's no pipeline stage that takes the receipt and composes follow-on actions (e.g., "if Y-gate is RED, queue a review brief; if FORK, surface the two paths for explicit selection"). No alternate-path exploration runtime — the LLM produces `paths` (A/B) in its output, but there's no runtime that branches on them, lets the user pick, and re-runs with the selection. No anticipatory briefing hook — the debrief email is scheduled for T+7, but there's no proactive "here's what to watch for based on your Y-gate state" briefing that surfaces sooner. The audit layer is fire-and-forget — no hook consumes audit results to alter subsequent behavior (D4 defers advisory injection). The pre-mortem document (FM-10) flags "No Hermes workflow composition of operators" as a structural gap — the harness can invoke operators but can't compose them into workflows. There's no receipt-created event or webhook that downstream consumers can subscribe to.

**Next step.** Define the smallest concrete post-compass hook: a receipt-created event (or simple webhook) that one downstream consumer can subscribe to. Start with one anticipatory briefing use case — enrich the receipt confirmation email or a follow-up notice with Y-gate-driven guidance (e.g., YELLOW → "your bearing is provisional; re-run after the horizon closes"; RED → "this decision has conviction blockers; see the court verdicts"). This is a small extension of the existing email path, not a new composition layer, and it realizes the anticipatory-briefing piece of the hook vision without requiring workflow composition infrastructure that doesn't exist yet.

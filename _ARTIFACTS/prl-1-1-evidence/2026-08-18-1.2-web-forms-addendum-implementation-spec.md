# 1.2-parallel — Web forms delivery — implementation spec (pre-approval prep)

Written ahead of Todd's approval/payment on Addendum 1.2-A so the build starts same-day once
he signs off — not a new investigation. Reuses the exact mechanism from 1.1/1.2 chatbot
delivery (`2026-08-18-manual-wiring-steps.md`), different trigger only.

## What's the same as the chatbot leg
- **Same Zapier Catch Hook**, same Sugar Leads Create Record action, same field map
  (`account_name, first_name, last_name, lead_source, location_c, phone_work, email1`).
  One Zap can serve both triggers if the payload shape matches — no need to duplicate it,
  just point the WP form's submit handler at the same webhook URL used in #1 above.
- `lead_source` value differs: hardcode `"Web Site"` for this leg (not `"Chatbot"`) — matches
  the existing real-world value already confirmed live in prod for web-sourced leads
  ([[prl-sugar-zapier-sandbox-integration]]).

## What's different — the actual 1.2A build work
1. **Identify the current WP form mechanism.** Prior finding: Gravity Forms is what's on the
   site today, and it doesn't deliver to Sugar at all — only (partially) to email, which is
   the separate Barracuda/SMTP problem Jorge already touched. Confirm Gravity Forms still is
   the form plugin in use (don't assume — verify on the day) before building against it.
2. **Add a webhook step to the Gravity Forms submission** — Gravity Forms has a native
   Webhooks add-on; if it's already installed/licensed, this is a no-code admin-panel config
   pointing at the same Catch Hook URL. If not installed, that's the one real unknown cost
   driver for this addendum (licensing/plugin install lead time) — flag immediately if hit.
3. **Field mapping from the WP form to the webhook payload** — the form's existing field
   labels need mapping to the same 6 keys. Confirm the form's current field list before
   estimating this step; likely small (name/email/phone/message), possibly missing
   company/state entirely, which would need new form fields added (visible scope change,
   flag before building, don't silently add fields to a form Todd hasn't reviewed).
4. **No new DB table, no custom API route** — the `PrlWebLead` staging-table approach was
   built, tested, and deliberately reverted this session once the reuse-the-chatbot-mechanism
   path was confirmed cleaner. Don't rebuild it.

## Explicit non-goals for this addendum
- Not touching prod Sugar (`prlresins.sugarondemand.com`) — same staging-only scope as 1.1/1.2.
- Not fixing rep routing — stopgap sweep already covers both delivery legs equally.
- Not building a `location_c` free-text normalizer — same raw-passthrough approach as the
  chatbot leg, consistent behavior across both trigger sources.

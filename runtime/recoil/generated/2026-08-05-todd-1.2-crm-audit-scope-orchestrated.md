## Product requirements (what the audit must DELIVER)
1. **Fielding-event verification** — does Sugar capture when a lead was first worked (status change / first
   activity / call log)? Determines whether the 4-hour metric is measurable or needs an auto-proxy.
2. **OEM↔molder data-model resolution** — the central complexity. How (or whether) Sugar models the two
   entangled personas: account-to-account links (does an OEM record relate to its molders?), the
   `OEM Profile` / `Type` (Captive) / `Focus Five` / `Competitors` fields, who holds the **spec** vs the
   **PO**, and how pricing flows OEM→molder. Output: exists-vs-net-new + a modeling recommendation.
3. **Territory model** — currently a global object; map to the delivered rep→state CSV; resolve the
   Distribution states, NY/PA sub-region splits, and Canadian provinces.
4. **Baseline** — volume, close rate, avg deal size by region + source (the net-new benchmark vs the $15K).
5. **Attribution** — quantify the $26.5M no-source; the 231 competitor-tagged opps as ICP/displacement
   signal; the Lead Forensics pipeline-vs-won test (the $15K displacement proof).
6. **Realized revenue + time-to-value** — from Position Data / Sales Numbers (the lagging clock; ship-and-collect).
7. **Net-new-vs-exists ledger** — every finding tagged: use an existing field/config, or build net-new.

## Design requirements
- **Deterministic + verifiable, 0% inference-as-fact.** Every finding traces to a queried record/field;
  ambiguous items are flagged, not asserted (same anti-hallucination floor as the chatbot KB).
- **Read-only.** The audit never writes to Sugar (sandbox-first applies even to reading).
- **Concise-return discipline.** Each sub-agent returns a compact structured verdict, never raw rows, so the
  orchestrator's context stays lean (token efficiency, per the OCR-audit pattern that worked).
- **OEM↔molder is cross-object** (Accounts × Opportunities × Quotes), so it is a synthesis stage, not one query.

## Implementation — sub-agent orchestration (graph; token-efficient)
Fan-out one **task-specialized sub-agent per Sugar object** (parallel), each auditing its object against the
drill-downs and returning a JSON verdict; then a synthesis stage resolves the cross-object questions. The
orchestrator holds only verdicts, never raw data. Runnable as a Workflow (fan-out → synthesis → consolidate).

**Phase 1 — fan-out (parallel, read-only, one agent per object):**
| Agent | Object | Returns (verdict schema: found · fields · gaps · exists|netnew · evidence-refs) |
|---|---|---|
| A1 | Opportunities | won-rate + avg deal by source; $26.5M no-source count; Lead Forensics pipeline-vs-won; digital-vs-total |
| A2 | Accounts | OEM Profile / Type / Focus Five / Competitors fields; **account↔account relationships** (OEM→molder?); territory field |
| A3 | Leads | 6 required fields; email coverage; lead_source picklist; **fielding-event timestamps** (status history / first activity) |
| A4 | Quotes | quote→win conversion; most-quoted grades (demand signal) |
| A5 | Position Data / Sales Numbers | realized revenue; time-to-value; at-risk accounts |

**Phase 2 — synthesis (consume Phase-1 verdicts, no re-query of raw rows):**
- **S1 OEM↔molder model** ← A1+A2+A4: how the relationship is (isn't) modeled + the net-new design
  (related-account link, spec-holder vs PO-holder flag, pricing-flow field).
- **S2 Metric + attribution + baseline** ← A1+A3+A5: fielding-event availability (→ 4-hr metric or proxy);
  the baseline; the response-time-vs-win-rate retro-analysis feasibility.

**Phase 3 — consolidate:** one report = the net-new-vs-exists ledger + the OEM↔molder modeling recommendation
+ the metric decision + the baseline. This is the CRM Data Reality output.

**Why this shape is token-efficient:** each agent reads only its object's data via CLI/API and returns a
compact verdict; the main loop never ingests raw CRM rows. Parallel fan-out = wall-clock ~= slowest single
object. Same delegation that kept the 95K-token OCR audit out of the main context.

## Outputs → what it feeds
